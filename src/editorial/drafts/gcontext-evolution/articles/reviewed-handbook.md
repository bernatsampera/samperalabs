An edit can preserve the right fact and still damage its document. The handbook flow therefore separates a proposed change from the files that later sessions will read.

The handbook is a folder of readable project documents. Project rules define what to retain, what to ignore, and how to write. Folder guides provide more specific instructions about placement.

## Inspect the change before accepting it

After a session, gcontext extracts candidate information, finds related facts, and proposes changes to a copy of the handbook.

| Step | What becomes available for inspection |
| --- | --- |
| Extract useful information | Candidate findings with supporting source text |
| Find related knowledge | Existing material that may need attention |
| Prepare an edit | Changes to the handbook files |
| Accept the proposal | An updated handbook for later use |

Rejection leaves the handbook unchanged. Acceptance checks whether relevant files and settings changed after the proposal.

In the illustrative export example, the proposal changes the guide from Settings to Reports. Review provides a chance to check that the edit removes the outdated instruction and preserves the rest of the procedure.

This does not guarantee that every affected passage has been found. The proposed changes still need inspection.

## A reviewed update must still prove useful

The reviewed end-to-end run on 31 October was a milestone for this flow. Earlier storage experiments already existed.

The local transcript reader supports Claude Code. Other systems can supply session packages, which is different from full transcript support for every agent.

The flow connected capture and approval. It did not establish that another session would find the accepted information, use it correctly, or complete its task more efficiently.

That required a separate evaluation of reading and use.
